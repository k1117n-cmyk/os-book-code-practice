### 3. 環境構築のつまずき: `python3.12 -m venv .`

#### 起きたこと

書籍の環境構築では、仮想環境を作るコマンドとして次のような形が出てくる。

```sh
python3.12 -m venv .
```

このコマンドは、現在いるディレクトリそのものを仮想環境にする。

そのため、実行したディレクトリ直下に `bin/` などの仮想環境用ディレクトリやファイルが作成された。

手元のシェル設定では、仮想環境ディレクトリ名を見て自動アクティベートする想定だったため、カレント直下に仮想環境が展開される形だと判定が崩れ、自動アクティベートが効かなかった。

#### 迷いやすい理由

`python -m venv .` の `.` は「このディレクトリに `.venv` を作る」という意味ではない。

`venv` の作成先としてカレントディレクトリそのものを指定している、という意味になる。

初学者の感覚では、仮想環境は `.venv/` という名前のディレクトリにまとまって作られると思いやすい。

しかし `.` を指定すると、`.venv/` という入れ物は作られず、作業ディレクトリ自体が仮想環境のルートになる。

#### 確認方法

実行後に、次のようなファイルやディレクトリが作られていれば、そのディレクトリ自体が仮想環境になっている。

```text
bin/
include/
lib/
pyvenv.cfg
```

自動アクティベートを使っている場合は、`.zshrc` などでどのディレクトリ名を仮想環境として検出しているかを確認する。

#### 対応

作業ディレクトリ直下に仮想環境の中身を散らしたくない場合は、仮想環境用のディレクトリ名を明示する。

```sh
python3.12 -m venv .venv
```

その後、必要に応じて有効化する。

```sh
source .venv/bin/activate
```

記事本文では、「書籍どおりに `.` を指定すると、カレントディレクトリ自体が仮想環境になる」ことを注意書きとして入れる。

```text
注意:
`python3.12 -m venv .` の `.` は、現在のディレクトリそのものを仮想環境にする指定です。

`.venv/` ディレクトリを作りたい場合は、`python3.12 -m venv .venv` のように作成先を明示します。
```

### 4. 最初の実行で迷ったこと: `Wrote hello.bin (28 bytes)`

#### 起きたこと

書籍では、次の2行のコマンドがまとめて提示されている。

```sh
python asm.py hello.asm
python emu.py hello.bin
```

1行目だけを単体で実行すると、ターミナルに次のようなログが表示された。

```text
Wrote hello.bin (28 bytes)
```

しかし、書籍側ではこのログの説明がなく、次の `emu.py` の実行結果である `Hello, World!` や `CPU halted.` の説明へ進んでいる。

そのため、「この `Wrote...` は想定どおりなのか」「書籍の出力と違うことが起きているのか」で迷った。

#### 原因

`python asm.py hello.asm` は、アセンブリコードを機械語のバイナリに変換する手順。

この段階では、プログラムはまだ実行されていない。

`Wrote hello.bin (28 bytes)` は、`hello.asm` のアセンブルに成功し、`hello.bin` という28バイトのバイナリファイルを書き出したという中間ログ。

その次の `python emu.py hello.bin` で、初めて `hello.bin` が CPU エミュレータ上で実行される、というのが書籍1-4の流れ。

ただし、現在の配布コードに含まれる `emu.py` は後半章向けに `os.bin` を起動する形になっているため、ブログでは書籍序盤の単体プログラムを動かすための `early.py` を使う案内を入れる。

#### 読むときの補助線

この箇所は、次のように分けて読むとわかりやすい。

- `python asm.py hello.asm`: `hello.asm` から `hello.bin` を作る
- `Wrote hello.bin (28 bytes)`: アセンブル成功の中間ログ
- `python emu.py hello.bin`: 書籍1-4では、作成した `hello.bin` を実行する手順として示されている
- `python early.py hello.bin`: ブログで公開する補助ファイルを使って、現在の配布コードでも同じ前提で実行する
- `Hello, World!` 以降: エミュレータ実行結果

記事本文では、複数行のコマンドがまとめて出てきたときは、1行ごとに「入力したコマンド」と「その直後の出力」を対応させて確認する、という注意書きを入れる。

```text
注意:
`Wrote hello.bin (28 bytes)` はエラーではなく、`asm.py` が `hello.bin` を正常に書き出したというログです。

この時点ではまだ `Hello, World!` は実行されていません。

書籍1-4では次の `python emu.py hello.bin` で、作成されたバイナリをエミュレータ上で実行します。現在の配布コードを使う場合は、ブログで公開している `early.py` を使って `python early.py hello.bin` のように実行します。
```

### 5. 最初のつまずき: `OSを読み込めませんでした。`

#### 起きたこと

`hello.asm` / `hello.bin` があるディレクトリで、次のように実行した。

```sh
python emu.py hello.bin
```

```text
OSを読み込めませんでした。
```

#### 原因

- 手元の `emu.py` は、引数で渡した `hello.bin` ではなく、`os.bin` を読む作りになっていた
- この `os.bin` はエミュレータ用の適当な入力ファイルではなく、Simple OS の本体
- そのため、`os.bin` がカレントディレクトリにない場所で実行すると `OSを読み込めませんでした。` になる

```python
with open("os.bin", "rb") as file:
```

たとえば、リポジトリ直下に `os.bin` がある状態で実行すると、OS 本体は読み込める。

```sh
python emu.py asm_code/hello.asm
```

```text
Welcome to Simple OS!
>
```

ただし、この場合に実行されているのは `asm_code/hello.asm` ではない。`emu.py` は引数を見ずに `os.bin` を読んでいるので、実際には `python emu.py` と同じく Simple OS が起動している。

#### 確認方法

```sh
grep -n 'open' emu.py
```

または

```sh
rg 'open|sys.argv' emu.py
```

#### ここでの切り分け

- `os.bin` を起動したいなら、リポジトリ直下で `python emu.py` を実行する
- 書籍1-4の `hello.bin` を直接実行したいなら、`os.bin` 起動用の `emu.py` ではなく、ブログで公開する初期章用の `early.py` を使う
- `early.py` は、書籍序盤の単体プログラムに合わせて、起動時引数で渡した `.bin` をアドレス `0x00000` から実行する

```python
with open(sys.argv[1], "rb") as file:
```

### 6. 次のつまずき: `IndentationError`

#### 起きたこと

`emu.py` が `os.bin` しか読まないなら、引数で `hello.bin` を読めるように書き換えればよいのでは、と思って修正した。

しかし、その途中で次のエラーになった。

```text
IndentationError: unindent does not match any outer indentation level
```

#### 原因

- Python はインデントでブロックを表す
- `if` と `else`、`try` と `except` のインデントがそろっていなかった
- そもそも書籍の流れでは、アセンブリコードは自作するが、CPUエミュレータなどの Python ファイルは用意されたものを使う前提
- そのため、初学者向けの記事では `emu.py` の改造を本文の主手順にしないほうがよい

#### 試行錯誤中の修正例

```python
if len(sys.argv) >= 2:
    binfile = sys.argv[1]
else:
    binfile = "os.bin"

try:
    with open(binfile, "rb") as file:
        prog = file.read()
        memory[0:len(prog)] = prog
except:
    print(f"{binfile}を読み込めませんでした。")
    sys.exit()
```

#### 記事での扱い

このエラー自体は Python のインデントミスだが、ブログ本文では「`emu.py` を自分で改造し始めると、書籍の本筋とは別の Python デバッグに入ってしまう」というつまづきポイントとして扱う。

結論としては、読者に `emu.py` を編集してもらうのではなく、書籍序盤の単体プログラム用に `early.py` を用意し、それを使ってもらう。

### 7. さらに次のつまずき: `Unknown opcode. type6 15 Halting.`

#### 起きたこと

```text
Unknown opcode. type6 15 Halting.
```

#### 原因

- `hello.bin` はメモリのアドレス `0x00000` から実行される前提
- しかし OS 起動用の `emu.py` では `PC` の初期値が `0x80000`
- これは `os.bin` の中の OS 本体を起動するための前提で、`hello.bin` を直接動かす前提とは違う

```python
'PC':  0x80000,
```

#### 修正方針

- `os.bin` を起動するなら、このままでよい
- 1-4の `hello.bin` を直接動かすなら、ブログで公開する `early.py` を使う
- `early.py` では、書籍序盤の実行結果に合わせて `PC` を `0x00000` にしている
- つまり、読者が現在の `emu.py` を手作業で変更する必要はない

```python
'PC':  0x00000,
```

- `SP` も初期版に合わせるなら `0xFFFFF`

```python
'SP':  0xFFFFF,
```

### 8. なぜ GitHub のコードと書籍の手順が食い違うのか

#### ポイント

- 書籍1-4の出力例は、`hello.bin` を直接読み込む初期版の `emu.py` を前提にしている
- その前提なら、書籍に載っている `SP: 000FFFFF`、`PC: 0000000C`、`PT: 00000000`、`VT: 00000000`、`CR: 00000000` という値になる
- 一方、リポジトリ直下の現在の `emu.py` は `hello.bin` ではなく `os.bin`、つまり OS 本体を起動する前提になっている
- そのため `python emu.py hello.bin` と入力しても、引数の `hello.bin` は読まれない
- GitHub の `main` は後半章向け、または最終形に近い状態なので、書籍序盤の手順とは一致しないことがある
- ブログでは、この差分を埋めるために、初期章用の `early.py` を公開して使えるようにする

#### 初めて読む人向けの整理

ここで起きているのは、レジスタ値の計算ミスではなく、実行しているプログラムが違うという問題。

書籍の原稿や序盤章の検証では、次のような初期版の `emu.py` が使われていたと考えると自然。

```python
with open(sys.argv[1], "rb") as file:
```

この形なら、`python emu.py hello.bin` で本当に `hello.bin` が読み込まれる。

しかし、現在ダウンロードできるリポジトリの `emu.py` は、後半章で OS を起動できるように変更されたあとの形になっている。

```python
with open("os.bin", "rb") as file:
```

そのため、書籍どおりに `python emu.py hello.bin` と実行しても、実際には `os.bin` の Simple OS が起動する。
この状態で表示されるレジスタ一覧は、`hello.bin` の終了状態ではなく、Simple OS を `exit` で終了した状態。

つまり、書籍の出力例そのものは `hello.bin` 直接実行の結果として正しい。
ただし、現在の配布コードをそのまま使うと、その前提どおりには動かない。

そのため記事では、`emu.py` を読者の手元で書き換えるのではなく、序盤用の補助エミュレータとして `early.py` を用意した、と説明する。書籍ではアセンブリコードを自作し、それ以外の Python ファイルは用意されたものを使う前提なので、ブログ側でも同じ感覚で `early.py` をダウンロードして使える形にする。

### 9. 書籍3-3の誌面構成で迷いやすいところ

#### 起きたこと

3-3「アセンブリ言語でプログラムを作成してみよう」では、図9として `mul.asm` のアセンブリコードが提示される。

このコードは、256 を 16 倍した結果を、10進数の `4096` と 4桁の16進数の `0x1000` で表示する例。

しかし、図9の直後にあるアセンブリコード自体の説明は、実質的には次の内容だけで終わっている。

- 数値を指定した書式で表示するため、システムコール2番を呼び出している
- システムコール2番では、`R8` に表示したい数値データを入れる
- `R9` に書式指定用文字列の先頭アドレスを入れる
- 書式指定用文字列は、Python の組み込み関数 `format()` で指定できる形式で書く

その次の行から、説明は Python の `format()` で使う書式指定用文字列の説明に切り替わる。

#### 迷いやすい理由

ここでは、アセンブリの命令列そのものを順番に解説してくれる流れに見える。

ところが実際には、図9のコード中にある次の2つの文字列を理解するために、途中から Python の書式指定の話へ移っている。

```asm
fmt_str1:
    .STRING ""

fmt_str2:
    .STRING "#04x"
```

本文ではこの切り替わりに見出しがないため、「アセンブリの説明を読んでいたはずなのに、急に Python の説明になった」と感じやすい。

また、なぜアセンブリの章で Python の `format()` の話をしているのかも、初見では置き去りになりやすい。

#### 読むときの補助線

ここで Python の説明が出てくる理由は、CPUエミュレータやシステムコールの実装側が Python で書かれているため。

アセンブリプログラムから見れば、`SYSCALL 2` は「`R8` の数値を、`R9` が指す書式指定文字列に従って表示する命令」のように使う。

一方、その表示処理を実際に実行しているのは Python 側のエミュレータなので、書式指定文字列も Python の `format()` で解釈できる形式になっている。

つまり、図9の `fmt_str1` と `fmt_str2` はアセンブリ上のデータ定義だが、その文字列の意味は Python の書式指定ルールに従って決まる。

#### 記事に入れる注意書き案

このあたりで迷った人向けに、記事本文では次のような注意書きを入れる。

```text
注意:
ここから先は、アセンブリ命令そのものの説明ではなく、`SYSCALL 2` で使う「書式指定用文字列」の説明に切り替わっています。

`mul.asm` では `R9` に `fmt_str1` や `fmt_str2` のアドレスを入れてから `SYSCALL 2` を呼び出しています。この `fmt_str1` / `fmt_str2` の中身は、エミュレータ側の Python コードで `format()` に渡されるため、書式の意味は Python の書式指定ルールで決まります。

そのため、アセンブリの章なのに途中で Python の `format()` の説明が出てきます。ここは「アセンブリの文法説明」ではなく、「エミュレータが数値をどう表示するかの説明」として読むとつながります。
```

#### 図9から図10への流れの整理

- 図9: `mul.asm` のコード例
- 図9の下: `SYSCALL 2` と `R8` / `R9` の使い方を短く説明
- その次: `R9` が指す書式指定用文字列の説明として、Python の `format()` の仕様に移る
- 図10: `mul.asm` をアセンブルして実行した結果
- 図10の後: `mul.asm` の説明は深掘りされず、次の「円周率を1000桁計算する」例へ移る

このため、本文を読むときは、図9のアセンブリ全体を逐語的に解説する節ではなく、「数値表示用システムコールの使い方を見せる短い例」として捉えると理解しやすい。

#### OS 本体を起動する場合

リポジトリ直下に `os.bin` がある状態で、次のように実行する。

```sh
python emu.py
```

または、引数を付けても現在の `emu.py` では引数は使われない。

```sh
python emu.py asm_code/hello.asm
```

出力:

```text
Welcome to Simple OS!
>
```

この結果は、`asm_code/hello.asm` が実行されたという意味ではなく、`os.bin` の Simple OS が起動したという意味。

#### `pi.asm` を Simple OS の `exec` から実行する場合

円周率を1000桁計算する `pi.asm` は、書籍本文と GitHub の最新版で末尾の命令が違う場合がある。

書籍側では単体プログラムとして直接実行する流れに見えるため、最後が `HALT` になっている。一方、GitHub の最新版では、`exec` コマンドから起動できるように最後が `RET` に変更されている。

Git履歴でも、次の変更が確認できる。

```diff
-        HALT
+        RET
```

コミットメッセージは「`execコマンドで起動できるように終了方法を変更`」。

意味としては、次のように分けて考える。

- `HALT`: CPUを停止する。単体実行向け
- `RET`: 呼び出し元へ戻る。Simple OS の `exec` から起動する外部プログラム向け

現在の `emu.py` で Simple OS を起動し、OS のプロンプトから `pi.bin` を実行する場合は、`pi.asm` の末尾は `RET` にする。

実行前に、`pi.bin` をリポジトリ直下の `dir/` に置く必要がある。`exec pi.bin` はカレントディレクトリの `pi.bin` ではなく、エミュレータ内部で `dir/pi.bin` を開く実装になっている。

```sh
python asm.py pi.asm
mkdir -p dir
cp pi.bin dir/pi.bin
python emu.py
```

Simple OS が起動したら、プロンプトで次のように入力する。

```text
Welcome to Simple OS!
> exec pi.bin
```

`dir/pi.bin` が無い場合は、次のようなエラーになる。

```text
File open error.
```

このエラーは `pi.asm` の文法エラーではなく、`exec` が読む場所に `pi.bin` が置かれていないという意味。

#### 書籍1-4の `Hello, World!` を直接動かす場合

`hello.asm` があるディレクトリで、ブログで公開している `early.py` を使って実行する。

書籍では `python emu.py hello.bin` と説明されているが、現在の配布コードの `emu.py` は `os.bin` 起動用になっている。`early.py` は、その手前の章の単体プログラムを直接実行するための補助ファイル。

#### 実行コマンド

```sh
python asm.py hello.asm
python early.py hello.bin
```

#### 出力

```text
Hello, World!
CPU halted.
R0: 00000000
R1: 00000000
R2: 00000000
```

### 11. 学び

- Python はインデントに意味がある
- `python -m venv .` は、カレントディレクトリ自体を仮想環境にする
- `asm.py` の `Wrote ...` はエラーではなく、バイナリ生成成功の中間ログ
- エラーメッセージは「どの段階で失敗したか」を分けて見る
  - ファイル読み込み失敗
  - Python 構文エラー
  - エミュレータ実行時エラー
- `os.bin` は OS 本体なので、`hello.bin` の代わりに読まれている不要なファイルではない
- 書籍の出力例は `hello.bin` 直接実行の結果としては正しいが、現在の配布コードはその前提で動かない
- 書籍序盤の `hello.bin` を直接実行したい場合は、ブログで公開している `early.py` を使う
- Simple OS が起動している場合、`CPU halted.` とレジスタ一覧はプロンプトで `exit` して終了したタイミングで表示される
- 書籍と GitHub の `main` ブランチが常に同じ段階とは限らない
- Git履歴を見ると、章ごとのコード変化を追える
- `pi.asm` は単体実行なら `HALT`、Simple OS の `exec` から実行するなら `RET` にする
- `exec pi.bin` は `dir/pi.bin` を読むため、事前に `dir/` へバイナリを置く必要がある
- 書籍3-3の図9以降は、アセンブリ命令の説明から Python の書式指定文字列の説明へ見出しなしで切り替わるため、読み手側で話題の切り替わりを補う必要がある

### 12. まとめ

- リポジトリ直下の現在の `emu.py` は `os.bin` 起動用
- `os.bin` は Simple OS の本体
- `python3.12 -m venv .` を実行すると、作業ディレクトリそのものが仮想環境になる
- `Wrote hello.bin (28 bytes)` は、`hello.bin` の生成に成功したという正常なログ
- `python emu.py hello.bin` や `python emu.py asm_code/hello.bin` で出た `Welcome to Simple OS!` は、`hello.bin` ではなく `os.bin` が起動した結果
- 1-4の `Hello, World!` を直接動かすなら、ブログで公開している `early.py` を使う
- `pi.asm` の最新版は `exec` 実行向けに末尾が `RET` になっている。実行時は `pi.bin` を `dir/` に置いてから `python emu.py` を起動し、OSプロンプトで `exec pi.bin` と入力する
- つまずいたら、`open()` しているファイル名と `PC` 初期値を見る
- 3-3の `mul.asm` では、アセンブリの話から Python の `format()` の話へ切り替わる箇所に注意する
